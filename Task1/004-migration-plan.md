# ADR-004. Обратная совместимость и стратегия миграции данных

- **Статус:** Accepted
- **Дата:** 2026-04-28
- **Контекст:** Задание 1
- **Автор:** Вячеслав Стеблецов

## Контекст

Платформа GoFuture мигрирует с монолитной архитектуры (Django + PostgreSQL) к микросервисной архитектуре с доменными сервисами.

Ключевые ограничения:

- система находится в production с активными пользователями;
- недопустим downtime критических функций (поездки, платежи);
- необходимо сохранить совместимость с мобильными приложениями и внешними API;
- объём данных значительный (поездки, платежи, пользователи);
- миграция должна выполняться поэтапно.

## Требования

| **№** | **Требование** |
| :-: | :- |
| 1 | Миграция должна происходить без остановки системы |
| 2 | Должна быть обеспечена обратная совместимость API |
| 3 | Новые сервисы должны внедряться постепенно |
| 4 | Данные должны мигрироваться поэтапно без потери консистентности |
| 5 | Должна быть возможность отката изменений |
| 6 | Миграция не должна ухудшать пользовательский опыт |

---

## Решение

### 1. Механизм обратной совместимости

Используется комбинация следующих паттернов:

- **API Gateway**
    - единая точка входа для клиентов;
    - маршрутизация запросов между монолитом и новыми сервисами;
    - скрывает изменения архитектуры от клиентов;
    - обеспечивает rate limiting, auth и API versioning.

- **Legacy Compatibility Layer / Anti-Corruption Layer**
    - сохраняет обратную совместимость текущих API;
    - адаптирует legacy-контракты и DTO к моделям новых доменных сервисов;
    - изолирует новые сервисы от внутренней модели монолита;
    - маршрутизирует часть запросов в монолит, а часть — в новые сервисы;
    - снижает риск влияния legacy-модели на новые сервисы.

- **API Versioning**
    - поддержка версий API (v1 -> монолит, v2 -> микросервисы);
    - постепенный перевод клиентов на новые версии;
    - сохранение старых контрактов до завершения миграции клиентов.

- **Feature Flags**
    - управление маршрутизацией трафика;
    - поэтапное включение новых сервисов;
    - canary rollout для ограниченной доли пользователей;
    - быстрый rollback при ошибках.

---

### 2. Стратегия миграции данных

Используется поэтапный подход без применения Dual Write между монолитом и сервисами.

#### 2.1. Принципы

- каждый сервис становится владельцем своих данных;
- миграция выполняется инкрементально;
- исторические данные переносятся через backfill;
- изменения данных передаются через события;
- запись должна выполняться в один primary source of truth на каждом этапе;
- временная дубликация данных допускается только как read-модель или миграционная копия;
- все обработчики событий должны быть идемпотентными.

---

#### 2.2. Паттерны миграции

- **Transactional Outbox + CDC (Debezium)** *(основной способ)*
    - запись в БД сервиса и outbox-таблицу выполняется в одной транзакции;
    - Debezium читает WAL PostgreSQL и публикует события в RabbitMQ;
    - потребители обновляют свои локальные read-модели;
    - исключается проблема несогласованной записи в две системы.

- **Backfill**
    - исторические данные переносятся пакетно;
    - применяется для заполнения новых БД перед переключением чтения;
    - выполняется идемпотентно и с возможностью повторного запуска.

- **CDC из монолита**
    - на переходном этапе изменения в таблицах монолита публикуются через Debezium;
    - новые сервисы получают события и синхронизируют свои read-модели;
    - используется до момента передачи владения данными конкретному сервису.

- **Read Switching (Strangler)**
    - сначала чтение выполняется из монолита;
    - после backfill и валидации чтение переключается на новый сервис;
    - переключение выполняется через API Gateway / Feature Flags.

- **Write Ownership Cutover**
    - для каждого домена определяется момент смены владельца записи;
    - после cutover запись выполняется только в новый сервис;
    - монолит больше не изменяет данные этого домена напрямую.

- **Parallel Run**
    - используется для критичных доменов, например Pricing и Payments;
    - новая реализация работает параллельно со старой;
    - результаты сравниваются до включения нового сервиса в production-flow.

---

### 3. План миграции по сервисам

| **Сервис** | **Стратегия миграции** | **Особенности** |
| :- | :- | :- |
| Notification | Новый сервис + подписка на события | Можно внедрить без миграции исторических данных; сервис потребляет события из RabbitMQ |
| Geography | Backfill справочников + интеграция с картами | Геозоны и справочные данные переносятся пакетно; маршруты и геокодинг обрабатываются через внешний API |
| Pricing | Parallel Run + Outbox/CDC | Новый сервис параллельно считает цену; результаты сравниваются с монолитом перед переключением |
| Fraud | Event-driven + CDC из монолита | Сервис строит риск-модель на событиях поездок, платежей и пользователей |
| Payments | Outbox + идемпотентные операции + cutover владения записью | Критичный домен; запись после cutover выполняется только в Payments Service; все операции имеют idempotency key |
| Driver | Backfill + CDC + постепенное переключение чтения/записи | Профили и статусы водителей мигрируются поэтапно; актуальность статусов поддерживается через события |
| Booking | Backfill + CDC + финальный write cutover | Центральный домен; мигрирует последним после стабилизации Driver, Pricing, Payments и Fraud |
| Analytics | Event-driven + ETL | Использует поток доменных событий и ClickHouse; не участвует в синхронном production-flow |

---

### 4. Этапы миграции

1. Введение API Gateway и Legacy Compatibility Layer / Anti-Corruption Layer.
2. Подготовка схем данных новых сервисов.
3. Настройка Transactional Outbox и CDC через Debezium.
4. Выполнение backfill исторических данных для первого домена.
5. Запуск read switching через Feature Flags.
6. Запуск parallel run для критичных доменов.
7. Выполнение write ownership cutover для выбранного домена.
8. Мониторинг метрик, сверка данных и проверка ошибок.
9. Повторение процесса для следующих доменов.
10. Деактивация legacy-кода и удаление зависимостей от монолита.

## Последствия

### Плюсы

- Отсутствие downtime при миграции.
- Снижается риск потери или рассинхронизации данных.
- Сохраняется обратная совместимость API.
- Возможен постепенный rollout и rollback.
- Новые сервисы получают независимое владение данными.
- Исторические данные мигрируются контролируемо через backfill.

### Минусы / риски

- Усложняется инфраструктура миграции.
- Требуется настройка Debezium и мониторинг CDC-пайплайнов.
- Возможны задержки доставки событий.
- Требуется идемпотентная обработка событий.
- На переходном этапе сохраняется временная дубликация данных.
- Необходима сверка данных между монолитом и новыми сервисами.

---

## Компромиссы

- Принимается временная сложность CDC-инфраструктуры ради отказа от Dual Write.
- Принимается eventual consistency для read-моделей и аналитических данных.
- Принимается временная дубликация данных как часть миграционного периода.
- Принимается поэтапная миграция вместо быстрого Big Bang-перехода.
