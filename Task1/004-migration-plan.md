# ADR-004. Обратная совместимость и стратегия миграции данных

- **Статус:** Accepted
- **Дата:** 2026-04-28
- **Контекст:** Задание 1 
- **Автор:** Вячеслав Стеблецов

## Контекст

Платформа GoFuture мигрирует с монолитной архитектуры (Django + PostgreSQL) к микросервисной архитектуре с доменными сервисами.

Ключевые ограничения:

- система находится в production с активными пользователями;
- недопустим downtime критических функций (поездки, платежи);
- необходимо сохранить совместимость с мобильными приложениями и внешними API;
- объём данных значительный (поездки, платежи, пользователи);
- миграция должна выполняться поэтапно.

## Требования

| **№** | **Требование** |
| :-: | :- |
| 1 | Миграция должна происходить без остановки системы |
| 2 | Должна быть обеспечена обратная совместимость API |
| 3 | Новые сервисы должны внедряться постепенно |
| 4 | Данные должны мигрироваться поэтапно без потери консистентности |
| 5 | Должна быть возможность отката изменений |
| 6 | Миграция не должна ухудшать пользовательский опыт |

---

## Решение

### 1. Механизм обратной совместимости

Используется комбинация следующих паттернов:

- **API Gateway**
    - единая точка входа для клиентов;
    - маршрутизация запросов между монолитом и новыми сервисами;
    - скрывает изменения архитектуры от клиентов.

- **Legacy Compatibility Layer (Adapter / Facade)**
    - проксирует legacy-запросы в монолит;
    - перенаправляет часть запросов в новые сервисы;
    - обеспечивает единый контракт API.

- **API Versioning**
    - поддержка версий API (v1 → монолит, v2 → микросервисы);
    - постепенный перевод клиентов на новые версии.

- **Feature Flags**
    - управление маршрутизацией трафика;
    - постепенное включение новых сервисов;
    - быстрый rollback при ошибках.

---

### 2. Стратегия миграции данных

Используется поэтапный подход:

#### 2.1. Принципы

- каждый сервис становится владельцем своих данных;
- миграция выполняется инкрементально;
- допускается временная дубликация данных;
- чтение и запись могут происходить в разные источники на переходном этапе.

---

#### 2.2. Паттерны миграции

- **Dual Write (временный)**
    - запись данных в монолит и новый сервис;
    - используется ограниченно для критичных сценариев.

- **Read переключение (Strangler)**
    - сначала читаем из монолита;
    - затем постепенно переключаемся на новый сервис.

- **Backfill**
    - исторические данные переносятся пакетно (batch);
    - используется для заполнения новых БД.

- **Event-driven синхронизация**
    - изменения публикуются в RabbitMQ;
    - сервисы синхронизируют данные через события.

---

### 3. План миграции по сервисам

| **Сервис** | **Стратегия миграции** | **Особенности** |
| :- | :- | :- |
| Notification | Новый сервис без миграции | Можно внедрить без зависимости от данных монолита |
| Geography | Интеграция с внешними API + частичный backfill | Минимальная зависимость от монолита |
| Pricing | Event-driven + parallel run | Проверка корректности расчётов |
| Fraud | Event-driven | Работает на потоках событий |
| Payments | Dual write + строгий контроль | Критичные данные, требуется идемпотентность |
| Driver | Backfill + постепенное переключение | Состояние водителей должно быть актуальным |
| Booking | Последний этап, сложная миграция | Центральный домен, требует полной готовности остальных сервисов |
| Analytics | Полностью event-driven | Использует события из всех сервисов |

---

### 4. Этапы миграции

1. Введение API Gateway и Compatibility Layer
2. Выделение первых сервисов (Notification, Geography)
3. Настройка event-driven коммуникации (RabbitMQ)
4. Постепенное выделение доменов (Pricing, Fraud, Payments, Driver)
5. Миграция Booking (финальный этап)
6. Деактивация и удаление монолита

---

## Последствия

### Плюсы

- Отсутствие downtime при миграции
- Возможность постепенного перехода
- Снижение рисков production-инцидентов
- Обратимость изменений (rollback)
- Независимое развитие сервисов

### Минусы / риски

- Временное усложнение архитектуры
- Дублирование данных на переходном этапе
- Необходимость поддержки двух систем
- Повышенные требования к мониторингу

---

## Компромиссы

- Принимается временная дубликация данных ради снижения риска
- Увеличивается сложность системы на период миграции
- Увеличиваются затраты на поддержку переходной архитектуры
