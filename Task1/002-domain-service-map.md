# ADR-002. Карта доменных сервисов GoFuture

- **Статус:** Accepted
- **Дата:** 2026-04-28
- **Контекст:** Задание 1
- **Автор:** Вячеслав Стеблецов

## Контекст

После фиксации нефункциональных требований необходимо определить целевую карту доменных сервисов.  
Карта сервисов нужна для декомпозиции текущего Django-монолита на независимые доменные области, соответствующие продуктовым командам GoFuture.

## Требования

Сформировать целевые доменные сервисы для следующих продуктовых направлений:

- Booking
- Driver
- Pricing
- Payments
- Notification
- Geography
- Analytics
- Fraud

Для каждого сервиса необходимо определить его ответственность и границы владения.

## Решение

### Карта доменных сервисов

| **Домен / сервис** | **Ответственность** | **Границы сервиса** |
| :- | :- | :- |
| Booking Service | Управление жизненным циклом поездки | Создание поездки, изменение статуса, отмена, завершение поездки |
| Driver Service | Управление водителями | Профиль водителя, статус доступности, смены, назначение водителя |
| Pricing Service | Расчёт стоимости поездки | Базовый тариф, динамическое ценообразование, коэффициенты спроса |
| Payments Service | Обработка оплат и выплат | Оплата поездки, возвраты, выплаты водителям, интеграция с платёжными провайдерами |
| Notification Service | Отправка уведомлений | Push-уведомления, SMS/email-сценарии, шаблоны сообщений |
| Geography Service | Геоданные и работа с картами | Геокодинг, маршруты, зоны, интеграция с картографическими сервисами |
| Analytics Service | Аналитика и отчётность | Сбор событий, витрины данных, отчёты, real-time analytics |
| Fraud Service | Антифрод-проверки | Проверка подозрительных поездок, платежей, пользователей и водителей |

### Общие платформенные компоненты

| **Компонент** | **Назначение** |
| :- | :- |
| API Gateway | Единая точка входа для клиентских приложений и внешних партнёров |
| Identity Provider | Аутентификация и авторизация пользователей, водителей, партнёров и сервисов |
| Event Bus | Асинхронный обмен событиями между сервисами |
| Observability Platform | Метрики, логи, трассировка и алертинг |
| CI/CD Platform | Независимая сборка, тестирование и деплой сервисов |

## Последствия

- Каждый доменный сервис получает чёткую зону ответственности.
- Продуктовые команды могут развивать сервисы независимо.
- Снижается связанность между частями системы.
- Появляется возможность независимого масштабирования сервисов.
- Для дальнейшей декомпозиции потребуется определить порядок выделения сервисов и стратегию миграции данных.
