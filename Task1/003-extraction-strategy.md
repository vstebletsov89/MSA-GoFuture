# ADR-003. Стратегия выделения сервисов из монолита GoFuture

- **Статус:** Accepted
- **Дата:** 2026-04-28
- **Контекст:** Задание 1 
- **Автор:** Вячеслав Стеблецов

## Контекст

GoFuture переходит от монолитной Django-архитектуры к микросервисной архитектуре.  
Текущая система обслуживает пассажиров, водителей, корпоративных клиентов и внешние интеграции внутри единого монолита и общей базы данных.

Ключевые ограничения:

- система уже находится в production;
- простой критических функций недопустим;
- текущий MTTR превышает 4 часа;
- пиковые нагрузки вызывают каскадные отказы;
- необходимо сохранить работу мобильных приложений, корпоративного портала и внешних интеграций;
- целевой time-to-market новых функций — до 2 недель.

Следовательно, миграция должна быть постепенной, управляемой и обратимо совместимой.

## Требования

Стратегия выделения сервисов должна:

| **№** | **Требование** |
| :-: | :- |
| 1 | Минимизировать downtime при миграции |
| 2 | Позволять постепенно выделять домены из монолита |
| 3 | Сохранять обратную совместимость для клиентских приложений и внешних API |
| 4 | Поддерживать независимый деплой новых сервисов |
| 5 | Позволять быстро откатывать изменения при ошибках |
| 6 | Снижать риск каскадных отказов |
| 7 | Поддерживать поэтапную миграцию данных |

## Решение

Использовать **Strangler Fig Pattern** как основную стратегию выделения сервисов.

Для снижения рисков дополнительно использовать:

- **Branch by Abstraction** — внутри монолита для безопасного переключения логики на новый сервис;
- **Parallel Run** — для критичных доменов, где требуется сравнение результата старой и новой реализации;
- **Feature Flags** — для постепенного включения новых сервисов;
- **API Gateway / BFF** — для сохранения стабильного внешнего API;
- **Anti-Corruption Layer** — для изоляции новых сервисов от модели данных монолита.

Big Bang-подход отклоняется из-за высокого риска простоя, невозможности безопасного отката и недопустимого влияния на production.

## Целевая стратегия

Миграция выполняется поэтапно:

1. Перед монолитом вводится API Gateway / BFF.
2. Для каждого выделяемого домена создаётся новый сервис.
3. Клиентский трафик постепенно маршрутизируется через Gateway:
    - сначала в монолит;
    - затем частично в новый сервис;
    - затем полностью в новый сервис.
4. Для критичных сценариев используется Parallel Run:
    - монолит и новый сервис обрабатывают одинаковые события;
    - результаты сравниваются;
    - новый сервис не влияет на production до подтверждения корректности.
5. После стабилизации трафик полностью переводится на новый сервис.
6. Старый код домена удаляется из монолита.
7. Данные мигрируются поэтапно в соответствии с ADR-006.

## Очерёдность выделения сервисов

| **Этап** | **Сервис** | **Обоснование** |
| :-: | :- | :- |
| 1 | Notification Service | Низкая доменная связанность, безопасный первый кандидат для проверки пайплайна выделения сервисов |
| 2 | Geography Service | Чёткая граница, внешняя интеграция с картами, можно вынести без сильного влияния на транзакционное ядро |
| 3 | Pricing Service | Высокая бизнес-ценность, требуется real-time динамическое ценообразование, можно запускать в parallel run |
| 4 | Fraud Service | Может работать асинхронно на событиях поездок и платежей, снижает риск влияния на основной поток |
| 5 | Payments Service | Критичный домен, требует аккуратной миграции, идемпотентности и обратной совместимости |
| 6 | Driver Service | Высокая нагрузка и связь с Booking, требует отдельной модели доступности и статусов водителей |
| 7 | Booking Service | Центральный домен с максимальной связанностью, выносится после стабилизации зависимых сервисов |
| 8 | Analytics Service | Выделяется через event stream и отдельные read-модели после стабилизации доменных событий |

## Почему Booking не выделяется первым

Booking является центральным доменом платформы и связан с:

- Driver;
- Pricing;
- Payments;
- Geography;
- Notification;
- Fraud;
- Analytics.

Выделение Booking первым создаёт максимальный риск регрессий и каскадных отказов.  
Поэтому сначала выделяются менее связанные сервисы и сервисы поддержки бизнес-процесса.

## Последствия

### Плюсы

- Минимальный downtime при миграции.
- Возможность поэтапного отката.
- Сохранение обратной совместимости для клиентов.
- Снижение риска production-инцидентов.
- Возможность валидировать новые сервисы на реальном трафике.
- Постепенное снижение размера и сложности монолита.

### Минусы / риски

- Временное сосуществование монолита и микросервисов усложняет эксплуатацию.
- Появляется дублирование логики на переходном этапе.
- Требуется маршрутизация трафика и feature flags.
- Требуется контроль консистентности данных при параллельной работе.
- Миграция займёт несколько этапов, а не один релиз.

## Компромиссы

- Принимаем более долгую миграцию ради снижения production-рисков.
- Принимаем временное усложнение архитектуры ради обратимости изменений.
- Принимаем необходимость поддержки старого и нового API на переходный период.
- Используем Parallel Run только для критичных доменов, чтобы не усложнять все сервисы без необходимости.
